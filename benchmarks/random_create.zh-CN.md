# 随机访问与创建优化

[English](random_create.md) | [简体中文](random_create.zh-CN.md)

本地对照基线为 `43e18e1`（实现与 `3fcda56` 相同），优化版为其后的工作区改动。
这不是新的 EnTT 对比，不覆盖或替换[已发表的接入重测](ecs_comparison.zh-CN.md)。

## 改动与取舍

- 将组件 deque 替换为独立分配的页面，每页元素数为 2 的幂，目标 4 KiB；更大类型每页一个元素。
  本机 MSVC STL 对 8 字节元素每块只放 2 个，新页可放 512 个，并省去 deque 的环绕映射寻址。
- 追加和预留容量不移动已有组件；Reserve 分配原始内存但不构造 T。
  删除仍为交换删除，资源立即析构，原有引用失效边界不变。
- 删除后保留空页供复用，ClearComponent、ClearAll 或存储析构时释放组件页。
  因此会保留峰值容量，每个池可能存在一页未用满的空间；不是所有场景都更省内存。
- 死亡槽位保留下一代编号，但内部句柄索引设为 0。IsAlive 仍检查有效性、范围及完整句柄一致性，
  省去一次 alive 数组读取。空句柄、过期句柄和预先构造的下一代句柄在槽位复用前均无效。
  实体枚举仍使用 alive 数组。
- 缓存空 archetype ID，避免每次 Create 重复查询。

## 测试方法

Windows x64、MSVC 19.50.35724 Release，10 万实体，两个 8 字节组件。
新旧程序使用相同基准源码。`run_random_create.ps1` 将子进程固定在逻辑 CPU 0（亲和掩码 1），
每轮交替新旧顺序，运行六轮、舍弃首轮，表格取其余五轮中位数。
密集和稀疏场景放在独立进程，避免上一场景的堆状态影响下一场景。

早期不限制调度的测量波动明显，连密集操作也受影响；下述数据来自隔离进程并固定 CPU 后的测量。
共享机器仍存在噪声，绝对时间不能直接与之前未固定 CPU 的报告比较。
所有访问、创建及查询校验和一致，覆盖率候选量也一致。

## 完整操作耗时

`access_paths.cpp`，单位毫秒。创建交替执行 Create 和两次 Add，不预留池容量。
随机读取按固定打乱顺序执行十轮；增删第三个组件十轮；遍历更新 200 次。

| 存储 | 操作 | 基线 ms | 优化后 ms |
| --- | --- | ---: | ---: |
| 稀疏 | 创建并添加两个组件 | 10.8015 | 7.2465 |
| 稀疏 | 复用 ForEach，更新 200 次 | 56.4447 | 37.2220 |
| 稀疏 | 新建 ForEach，更新 200 次 | 55.4720 | 35.9398 |
| 稀疏 | 随机 Get 十轮 | 24.5535 | 10.7215 |
| 稀疏 | 增删十轮 | 15.8115 | 10.9786 |
| 稀疏 | 销毁全部实体 | 2.5893 | 1.4869 |
| 密集 | 创建并添加两个组件 | 21.6508 | 20.1904 |
| 密集 | 复用 ForEach，更新 200 次 | 10.9662 | 10.9150 |
| 密集 | 新建 ForEach，更新 200 次 | 10.9627 | 9.8728 |
| 密集 | ForEachBatch，更新 200 次 | 5.7977 | 6.1099 |
| 密集 | 随机 Get 十轮 | 18.8834 | 15.3622 |
| 密集 | 增删十轮 | 186.1050 | 185.7160 |
| 密集 | 销毁全部实体 | 1.3116 | 1.6976 |

该负载下稀疏随机读取耗时减少约 56%，创建减少 33%，增删减少 31%，销毁减少 43%。
但密集销毁在本轮样本中变慢约 29%（约 0.39 ms），因此不能称为全面提速。
密集遍历、增删整体接近，短操作仍容易受调度、代码和堆布局影响。结果不代表整个引擎帧率。
原始数据：[基线](paged_access_baseline.csv)、[优化版](paged_access_optimized.csv)。

## 创建与随机访问拆分

`random_create.cpp` 先创建所有实体，再分两轮添加组件，其分配模式与上面的交替创建不同。
池 Get 绕过 World 的注册/句柄检查；ComponentAt 还绕过稀疏索引。
编译器和缓存行为不同，不能直接相减来推导单项成本。随机读取均为十轮。

| 是 | 预留本身 | 0.0392 | 0.5661 |

| 是 | 添加第一个组件 | 2.9095 | 0.9971 |

原始数据：[基线](random_create_baseline.csv)、[优化版](random_create_optimized.csv)。

## 查询覆盖率回归

原 Where/校验和基准在同一逻辑 CPU 上交替运行六对进程，舍弃第 0 对。
每个进程预热十次查询、计时 200 次。

| 覆盖率 | 两版候选量 | 基线 µs/查询 | 优化后 µs/查询 |
| --- | ---: | ---: | ---: |
| 1% | 1,000 | 2.8805 | 2.3235 |
| 10% | 10,000 | 33.9990 | 22.6135 |
| 100% | 100,000 | 299.7120 | 204.0760 |

[原始输出](paged_coverage.txt)。候选量和校验和一致，说明这些负载中的查询匹配结果保持不变。

## 验证与复现

Release CTest、MSVC AddressSanitizer（RelWithDebInfo，启用 /EHsc）及使用新头文件的
TomCat dev_ekit SceneWorldRegression 均通过。
新增测试覆盖页增长/预留、大组件和对齐、页边界构造失败、复制失败、复制移动所有权、
资源即时释放、清空复用，以及死槽位拒绝下一代句柄。
没有重建完整 TomCat 应用，也没有修改其固定依赖；未增加批量创建 API，未迁移组件存储类型。

```powershell
cmake -S . -B build_sparse_query -DEKIT_BUILD_BOIDS=OFF -DEKIT_BUILD_QUERY_BENCHMARK=ON
cmake --build build_sparse_query --config Release
ctest --test-dir build_sparse_query -C Release --output-on-failure
./benchmarks/run_random_create.ps1 -BaselineDirectory <baseline-bin-directory> -OptimizedDirectory ./build_sparse_query/Release
```

基线使用同一份基准源码、`43e18e1` 头文件和相同编译参数。
脚本要求两个目录均有 random_create、access_paths、sparse_query 对应可执行文件，结束后恢复 shell 的 CPU 亲和设置。
可选命令行参数指定单轮编号（0–5）；access_paths 第二个参数可为 `sparse` 或 `dense`。
